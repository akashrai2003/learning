# Strategy: improve your offer prospects before becoming a different engineer

## The near-term opportunity

You have stronger evidence than a generic 'I built a chatbot' profile: production ingestion, retrieval, model serving, Docker-based deployment, GPU-memory constraints, asynchronous workflows, OCR failure analysis and client delivery. The problem is making the scope legible and independently assessable while passing ordinary software-engineering interviews.

Your pitch should connect a constraint to an engineering action and an observed result. For example: limited accelerator memory required changes to cache configuration and request batching; an offline deployment required reproducible artifacts and recovery workflows. Include exact numbers only where you can defend their measurement and are permitted to disclose them.

The new phone and C++ curriculum add a distinctive direction. They should not erase the production experience that can earn the next offer. In the next four months, an employer is more likely to trust a well-tested Python platform contribution plus a detailed incident analysis than a claim of kernel expertise after a few tutorials.

## Role map

| Role family | Fit now | Evidence to emphasize | Main gap to test |
|---|---|---|---|
| Applied AI / AI Engineer | Strongest initial lane | Retrieval, extraction, evaluation, backend integration and delivery | Python coding, evaluation rigor, system design |
| Backend Engineer — AI platform | Strong adjacent lane | APIs, queues, storage, retries, model integration and operations | SQL, concurrency, testing and service reliability |
| ML Platform / Inference Platform Engineer | Selective but credible | vLLM operations, benchmarking, containers, GPU debugging and residency | Source-level changes, observability and larger-scale architecture |
| AI deployment / forward-deployed engineer | Useful alternate lane | Client delivery, on-prem systems, requirement discovery and integration | Travel expectations, communication and commercial scope |
| Inference performance engineer | Stretch where platform-focused | Measured latency/memory work, profiling and a runtime contribution | Defensible methodology and source-level depth |
| CUDA kernel / compiler specialist | Longer-term selective lane | Future C++/SIMD/kernel artifacts | Direct systems programming and kernel optimization evidence |
| AI developer tools / technical solutions engineer | Optional lane | Debugging, examples, developer communication and OSS | Verify coding depth, compensation and actual role mix |

Do not reject a role solely because it says 'Senior' if the described scope and experience fit. Conversely, do not pursue a 5–8 year distributed-kernel role simply because you know its model names. Read must-have requirements and distinguish preferred qualifications. Use approximately 1–3 years as primary and flexible 2–4 year roles as adjacent; treat much higher requirements as explicit exceptions.

## Two parallel markets

Use a starting application allocation of roughly **50% global remote, 40% India/Bengaluru, 10% exceptional stretch**. These percentages are a planning choice, not an evidence-based conversion guarantee. Review after four weeks. If global geography exclusions dominate, shift more time to employers already able to hire in India. Keep some international exploration even while progressing domestic interviews.

For international roles separate: a company headquartered in the US/EU; a team based there; a role requiring residency there; and a company hiring in India. Only the last determines whether your current location is eligible. 'Remote Europe' or 'EMEA' is not an India-eligible label. A global EOR provider's presence does not prove a particular employer will use it.

## The positioning sentence

Draft: 'I build production AI systems under deployment and resource constraints: document intelligence, Python services, local LLM serving and evaluation. I am deepening inference-runtime and edge deployment skills through reproducible benchmarks and open-source work.'

Use this as an editable description of direction. Do not describe yourself as a kernel engineer, distributed-serving expert or open-source maintainer without corresponding work. Be precise about personal ownership versus team output.

## Your evidence inventory

For each major work item write: problem, constraints, your responsibility, decisions, alternatives, implementation, validation, failures and outcome. Suggested stories: model residency and switching; throughput/context tradeoffs; OCR disagreement handling; ingestion and retry design; air-gapped upgrade process; evaluation or grounded-answer failures.

For the reported aggregate throughput improvements, recover prompt lengths, concurrency, model/quant, runtime version, generation counts and measurement boundaries. Distinguish aggregate output tokens/s from a single user's speed. If those records cannot be shared, reproduce the concept publicly with a new benchmark rather than turning uncertain private numbers into public claims.

## Success measures you control

You control screened opportunities, evidence-backed applications, coding practice, completed experiments, thoughtful contributions and interview reviews. You do not control reach, maintainer response time or offer timing. Track both effort and conversion so you can change strategy instead of merely increasing volume.

By week 4 aim to have coherent public evidence and active applications. By week 8 aim to have diagnosed interview weaknesses and a reviewable contribution or equivalent technical artifact. By week 12 aim to be progressing serious processes. By week 16 aim to evaluate offers or make a clearly informed pipeline adjustment. These are operating milestones, not promises that external events happen on schedule.

# Time budget: one working plan alongside a full-time job

## Do not add two complete curricula together

The earlier 24-week study pack assumes roughly 17 hours a week. This career plan uses approximately **17.5 total hours a week**, including selected inference/C++ study. For the next 16 weeks, extend the previous learning calendar rather than doing both plans in full. Day numbers do not need to advance together.

Suggested weekly allocation: coding/interview foundations 4.5 hours; public project or OSS 4.5 hours; applications and relationship-building 3 hours; content/profile 1.5 hours; targeted C++/inference study 2.5 hours; review 1 hour. Total 17.5 hours. Technical project work also develops inference skills, so the separation is a planning aid rather than a perfect accounting taxonomy.

## A sustainable week

| Day | 150-minute session |
|---|---|
| Monday | 60 minutes coding, 60 minutes project/OSS, 30 minutes search |
| Tuesday | 60 minutes targeted C++/inference, 60 minutes interview/design, 30 minutes applications |
| Wednesday | 90 minutes project/OSS, 30 minutes preparing a technical post, 30 minutes relevant conversation |
| Thursday | 60 minutes coding, 60 minutes project/OSS, 30 minutes applications |
| Friday | 60 minutes targeted learning, 45 minutes mock/incident review, 45 minutes search and follow-up |
| Saturday | 60 minutes project/OSS, 45 minutes design/coding review, 45 minutes publishing and genuine replies |
| Sunday | 60 minutes funnel review, 30 minutes technical recap, 45 minutes next-week preparation, 15 minutes backlog cleanup |

This is a default pattern; the weekly files override it when there is a deliverable or interview. Optional 30-minute extensions must stay within your three-hour ceiling. If you have only two hours, remove optional work and reduce post frequency before cutting active interview preparation.

## During interview-heavy weeks

Treat a 60-minute interview as part of the day's learning time, and reserve another 20–30 minutes for preparation/debrief. Reduce content and new OSS scope first. Keep existing reviewer responses timely within your availability. Do not begin a large new contribution while handling final rounds.

## What to keep from the original curriculum

Keep compilation/types/ownership fundamentals; one stable model; the benchmark runner; Python reference operations; cache reasoning; numerical tests; and small native deployment exercises. These support interviews and public proof. Slow down the full educational engine and advanced Android integration if the offer pipeline needs attention.

Do not claim completion of the 24-week inference curriculum in 16 weeks through this combined plan. You are selecting high-value exercises and extending the rest. Resume the deeper schedule after the transition or when your weekly capacity allows it.

## Minimum viable week when work is busy

Complete one timed coding exercise with review; progress one existing application; qualify three roles; make one concrete project/OSS improvement; and write one short experiment note. Publishing can pause. A credible repository and a prepared interview outperform an exhausted content schedule.

## Weekly targets and limits

After the setup fortnight, start with 5–8 carefully screened applications, 3–5 contextual professional conversations, two posts based on real work, one mock segment, and one OSS work item in progress. These are suggested inputs, not required output quotas or expected replies. If researching eligibility consumes the time, prioritize fewer high-fit applications.

Maintain **one primary repo, one public flagship project, and at most one upstream PR in flight initially**. A second repo is a backup for blocked work, not another simultaneous commitment. Do not pay for GPU time before a contribution or experiment requires it and you have set a small explicit budget.

# First 14 days: begin the hiring process now

Use the detailed daily tasks in weeks 01 and 02. This page highlights the outputs that matter before adding more study.

## Days 1–3

Build an evidence inventory and verify employment dates. Separate internships, full-time roles and freelance periods; do not double-count overlapping months. Draft two resume variants: applied AI/backend and AI platform/inference serving. Identify one public benchmark project you can complete incrementally with existing hardware.

Output: two honest resume drafts, one role thesis, and a tracker with real source links. Unknown salary, region or level remains unknown.

## Days 4–7

Refine headline/About/Featured sections, establish a baseline coding score, and write one public project README with a narrow question. Inspect contribution guidelines for two candidate repos, then select one primary. Qualify the first five roles. Apply to strong fits before waiting for the project to look impressive.

Output: usable application materials, one repeatable experiment or documented initial failure, and a small screened pipeline. Posts are optional until there is evidence to show.

## Days 8–10

Run a benchmark with public inputs; retain raw records. Publish one short technical explanation only if the result is understandable and shareable. Inspect several recent merged PRs in your chosen subsystem and reproduce a small issue or documentation gap. Practice Python coding with explicit tests and a time limit.

Output: first evidence link, a contribution-scoping note, and an interview weakness list.

## Days 11–14

Complete targeted applications with role-specific evidence. Begin genuine conversations with engineers or recruiters whose work overlaps yours; use a concise, relevant message and do not assume a referral. Practice a 30-minute system-design case and record your explanation. Review the funnel and reduce any activity that produced noise instead of useful signal.

Output: a repeatable weekly routine, a tested project increment, a meaningful OSS next step, and a corrected pitch based on actual job requirements.

## Avoid these early traps

Spending two weeks perfecting a banner; claiming NPU support before testing; buying a large GPU because job descriptions mention distributed inference; sending the same referral request to dozens of strangers; starting five repositories; or waiting until you know C++ well enough to apply for Python-heavy AI engineering roles.

# Finding and qualifying opportunities

## Search for the work, not only the title

Use several title families: AI Engineer, Applied AI Engineer, Backend Engineer AI, ML Platform Engineer, Inference Platform Engineer, LLM Infrastructure Engineer, AI Deployment Engineer and Developer Tools Engineer. 'GenAI Engineer' can retrieve useful work but also many low-depth integration roles. Read actual responsibilities.

Start with direct company career pages, LinkedIn Jobs, YC Jobs and Wellfound. Search engines can discover ATS postings, but apply through a verified official destination. See the dated research snapshot (split-file location: `guides/research-snapshot.md`) for inspected examples and limitations.

## Search query bank

Run short focused searches and record what worked:

```text
("AI Engineer" OR "Applied AI Engineer") (India OR worldwide OR APAC) remote
("inference" OR "ML platform") engineer (India OR Bangalore OR Bengaluru)
("vLLM" OR "SGLang") (hiring OR careers OR engineer)
("LLM" OR "AI") "remote" "contractor" "India"
site:jobs.ashbyhq.com "AI" "India"
site:job-boards.greenhouse.io "inference" "India"
site:jobs.lever.co "machine learning" "remote"
site:ycombinator.com/companies "AI" "Remote" "India"
```

Query syntax varies by search engine and job board. Use 'posted recently' filters when available, but verify the actual listing; search crawl dates are not posting dates. Avoid excluding 'Senior' globally: some companies use it loosely while others attach a strict experience requirement.

## Eligibility gate before application effort

1. Is the role still present on the official site?
2. Does it allow working from India? What exact wording establishes that?
3. Is employment via an India entity, EOR or contractor route available, or still unconfirmed?
4. Is the experience requirement approximately aligned, flexible, or a hard mismatch?
5. Is the role's work compatible with your direction and schedule?
6. Is pay published, recruiter-confirmed, unknown, or clearly below your target?
7. Is the needed timezone overlap sustainable from Bengaluru?

Record eligibility as **confirmed India / explicitly worldwide but arrangement unconfirmed / unclear / excluded**. 'EU remote' does not pass the India gate. If a role is attractive but unclear, send one precise question before a long take-home assignment.

## A practical fit score

Use a 100-point local prioritization score: responsibility overlap 30; demonstrable evidence 25; level fit 15; location/arrangement clarity 15; compensation feasibility 10; personal constraints 5. Hard exclusions such as mandatory US residency override the total. This score is a planning tool, not a calibrated hiring prediction.

Suggested buckets: A for clear fit with strong evidence, B for adjacent or one resolved gap, C for selective stretch, and no-apply for hard exclusions. Spend most effort on A/B. A known employer with a glamorous title is not automatically A.

## Build a target list that stays useful

Keep around 20–30 company/team targets rather than hundreds of unreviewed bookmarks. For each: product, why your experience matters, relevant team, source URL, actual role if available, geography, level, pay status, and next action. Separate a **company watchlist** from **verified open role**. A company without an eligible role can remain a research target but should not inflate your application count.

Refresh highest-priority roles weekly. Archive closed roles and retain the reason; do not silently convert them into still-open recommendations. If an employer has a careers alert, set it up manually if you want it. This pack creates no scheduled alerts or recurring tasks.

## Application packet

For each serious role prepare: the appropriate resume, a two- or three-sentence fit explanation, one relevant public evidence link, and a short gap explanation when needed. A model-serving role should see the benchmark/incident case first; a document AI role should see evaluation and extraction evidence first.

Apply through the official process, then optionally send a relevant human a concise note with the role and evidence. A referral is helpful but not required to begin. Do not send multiple inconsistent applications to the same organization without tracking them.

## Recruiter qualification call

Ask what the team owns; level and experience flexibility; India eligibility and arrangement; currency and base/variable/equity split; overlap hours; interview stages; assessment expectations; expected start date; and whether your notice period is workable. Ask for the budget range early enough to avoid a large mismatched process. If a recruiter cannot answer, mark it unconfirmed rather than inventing a number.

## Remote roles versus AI evaluation projects

Coding-evaluation and model-training platforms can provide paid projects, but verify work scope, guaranteed hours, duration, review/payment rules and continuity. A high hourly headline is not a permanent engineering salary. Do not count an invitation or platform profile as an offer. Consider such projects selectively if they build relevant skills and do not interfere with your employment obligations.

## Review the funnel

If 15–20 well-qualified applications produce no conversations, inspect resume evidence, level and geography before sending 100 more. If screens happen but technical rounds fail, shift time to the specific failure category. If final rounds happen without offers, review communication, scope, references and compensation alignment. Small samples are noisy; treat these thresholds as prompts for diagnosis, not statistical proof.

# LinkedIn visibility based on engineering evidence

## The audience and the job

Write for engineers, engineering managers, technical recruiters and founders hiring for production AI systems. Your objective is that a relevant person can understand what you did, inspect the evidence and remember your specialty. Broad reach without relevant conversations is a weak career signal.

LinkedIn's official 2026 guidance emphasizes authentic perspective and discourages generic automated content [L1]. Its help page describes post analytics [L2]. Neither source establishes a guaranteed posting time, external-link trick or follower threshold for employment. Treat the posting cadence below as an experiment, not an algorithm claim.

## Profile structure

Headline draft: **AI Engineer | Production LLM systems, document intelligence and inference serving | Python, FastAPI, vLLM**. Add edge deployment once you have an artifact. Do not fill the headline with every library you've encountered or call yourself a kernel specialist prematurely.

About structure: one sentence on what you build; a paragraph on two production problems you owned; two or three verifiable results; a sentence on current public work; and the opportunities you seek. Explicitly state 'Based in Bengaluru; open to India roles and global teams able to hire remotely in India' if that reflects your preferences. Avoid putting current salary on the public profile.

Featured section: one concise technical case study, the flagship repository, a measured benchmark report, and optionally a merged contribution. A tutorial certificate can be secondary. The first screen should answer what you build and where the evidence is.

Experience entries should explain scope and personal responsibility. Label internships and full-time periods accurately. Check that resume, LinkedIn and application dates agree. Two years of overlapping projects do not become four years of employment.

## Your four content pillars

1. **Production inference:** latency, context budgets, memory residency, deployment failures and profiling.
2. **Document AI correctness:** table alignment, source evidence, disagreement evaluation and grounded extraction.
3. **Open-source engineering:** reproductions, regression tests, code review lessons and maintainers' accepted changes.
4. **Learning in public:** a C++ lifetime bug, cache implementation or Android measurement, with a clear learning label.

Start with two posts a week: one evidence-based result and one narrower lesson or investigation. If results are not ready, publish one useful post rather than inventing progress. Use an occasional longer article as the canonical case study and link shorter posts to it.

## The anatomy of a useful technical post

Begin with a concrete engineering problem: 'I measured whether keeping a small model resident changes application TTFT.' Then give the test setup, one result or failure, your interpretation, the main limitation, and a link to methods/code when shareable. A specific question invites a technical exchange: 'How do you distinguish preparation time from first-use cache effects on this backend?'

Avoid unsupported superlatives, universal speedup claims, generic motivational introductions and fabricated incidents. Distinguish reproduction from original discovery. Credit upstream work and coauthors. If an experiment has only three runs, say so instead of presenting a robust tail-latency conclusion.

## Formats

A short text post can explain an incident. A small chart can compare measured configurations. A code screenshot should be accompanied by selectable code or a repository link. A 30–60 second demo can show an offline request and cancellation. A document carousel can explain one concept with an experimental example; use it only if creating it does not consume the implementation time.

Do not make all posts a 'day N of learning' diary. Convert progress into something a practitioner can use: a diagnostic checklist, reproducible test, failure boundary or implementation tradeoff.

## Relationships and reach

Follow engineers working on your chosen repos and companies. Leave a few comments a week only where you can add a relevant observation, precise question or small reproduction. Read the linked work before commenting. Do not use engagement pods, automated comments or broad tagging. Maintainers are collaborators, not an audience you are entitled to recruit.

When someone engages substantively, reply with context. If a professional conversation develops, ask about their technical work or team before requesting favors. You may share a relevant application once, but do not turn every discussion into a referral request.

## Measurement

For each post record topic, artifact, time spent, impressions/reach if available, relevant technical replies, profile visits if available, evidence-link engagement if available, useful conversations and any attributed interview lead. Some platform fields vary; leave unavailable fields blank. Do not attribute every recruiter message to the latest post.

After four weeks compare topics and formats within your own modest sample. Keep what produces relevant conversations and credible evidence. Do not optimize solely for likes or conclude a universal best time from eight posts.

## Publishing boundaries for your experience

Your defense-related work requires particular care with what you can share. Use public/synthetic documents, public checkpoints and independently written code for the public artifact. Changing a client name does not make private data or employer-owned code publishable. Share a general engineering principle only within what you are allowed to disclose. This is a practical boundary for your actual work context, not a reason to avoid publishing safe independent experiments.

# Resume, profile and interview narrative

## Two focused resume variants

Keep a common factual record and change emphasis. The applied AI/backend version should lead with delivered systems, retrieval/extraction quality, APIs, queues and deployment. The platform/inference version should lead with serving, measurement, GPU memory, operational debugging and reproducible infrastructure. Neither should invent skills or alter dates.

Use a clean readable format, typically one page at your experience level unless substantial relevant evidence justifies a second. Include standard section names, visible text links and ordinary bullets. Check that the exported PDF is selectable and text extraction preserves meaning. No particular formatting guarantees an ATS pass.

## Evidence-based bullets

Use: action + owned component + constraint + validation/outcome. Draft examples below require fact-checking and disclosure approval; they are not ready-made claims.

- 'Built and deployed an on-prem document intelligence workflow spanning ingestion, storage, retrieval and model-serving integration; owned [specific components] and [release/recovery responsibilities].'
- 'Investigated inference memory and throughput limits on [publicly shareable hardware/model]; changed [specific configuration/code] and measured [metric] under [workload].'
- 'Developed extraction review and evaluation workflows for complex documents, separating model disagreement from confirmed errors through [method].'
- 'Implemented [queue/retry/checkpoint behavior] to recover from [failure], validated using [test or incident evidence].'

Replace brackets with verified details. Do not turn configuration tuning into a claim that you implemented the serving runtime. Do not describe offline experiment throughput as production traffic. If a result is a team outcome, identify your contribution accurately.

## Metrics audit

For every number ask: what was measured; where the raw evidence is; baseline and final configuration; workload; denominator; single-request versus aggregate; quality or reliability cost; permission to publish. If the answer is weak, remove the number or qualify it. A strong nonnumeric bullet is preferable to a misleading one.

## About section working draft

'I build production AI systems that connect document processing, backend services and local model inference. My work has included on-prem deployment, ingestion and retrieval workflows, evaluation, and debugging model-serving behavior under resource constraints.

I am now building public, reproducible experiments around inference latency, memory and deployment reliability, while developing C++ and edge-runtime skills. I am interested in applied AI and AI platform roles where I can own systems beyond the prototype stage. Based in Bengaluru, I am open to India roles and global teams able to hire remotely in India.'

Edit this into your voice and add approved concrete evidence. Do not publish it automatically. Avoid implying that all current work is public or open source.

## Six interview stories

Prepare two-minute and eight-minute versions of: hardest production failure; performance tradeoff; quality/evaluation failure; ownership under ambiguity; disagreement or collaboration; and a mistake you corrected. Use context, responsibility, choices, action, validation and lesson. Keep enough technical detail to withstand follow-up.

Your inference model-switching investigation can support a strong story if you can explain which process owned weights and cache, what happened on sleep/wake, how you detected behavior, alternatives considered and the actual fix. Do not repeat a remembered metric without recovering the test conditions.

## Strong introduction

In 60–90 seconds: current role and scope; one production system you owned; one concrete engineering problem; why this team fits your next step. Salary, full tool lists and a complete autobiography are not needed. For a remote team, mention written documentation and independent debugging as demonstrated habits rather than personality claims.

## Handling gaps

Say 'I have operated and investigated this runtime; my source-level contribution is [specific work]' instead of claiming deep kernel expertise. For Kubernetes or distributed inference gaps, explain the closest system you built and one focused exercise you completed. Acknowledge that a single GPU does not establish multi-node production experience.

## References and consistency

Ask potential references privately and only when needed; this pack sends no messages. Use the same job dates and role names across resume, LinkedIn and forms. Verify full-time versus internship transition dates. Current compensation of approximately 20 LPA is an input to negotiation planning, not a public headline or a market-value ceiling.

# Open-source contribution workflow

## The objective

Become useful in one relevant subsystem. A good contribution gives maintainers a clear problem, a small understandable change and appropriate evidence. Merged work can support hiring, but maintainers do not owe reviews, endorsements or referrals. Track learning and reviewability even when merge timing is outside your control.

Choose a primary repo based on overlap with your current work and hardware. For your near-term timeline, start with vLLM Python-facing behavior, GuideLLM benchmarking, or Docling correctness/export work. Keep SGLang as a deliberate alternative. # Interview preparation for the next offer

## Prepare for the role you can credibly win

Use Python as your default interview language unless the role explicitly tests another language. Your immediate bottleneck is likely consistent coding, backend depth, system-design reasoning and defensible project stories, not knowing every inference paper. Continue C++ fundamentals, but do not switch all coding practice to beginner C++ while pursuing Python-heavy jobs.

Confirm each employer's process early. Some use algorithmic interviews; others use practical tasks, debugging or take-homes. The structure below is your preparation plan, not a claim that every company uses these rounds.

## Coding practice method

For a 60-minute session: 5 minutes restate requirements and examples; 10 minutes choose a data structure and complexity; 25 minutes code; 15 minutes test and explain; 5 minutes log the failure category. Revisit missed questions after two days and one week. Count independently solved and explained problems, not merely watched solutions.

Cover arrays/maps/sets, two pointers, sliding windows, sorting, binary search, stacks/queues, heaps, tree traversal and graph BFS/DFS. Add basic dynamic programming when target interviews require it. Aim initially for approximately 30–40 well-reviewed problems over the cycle, supplemented by practical tasks. Increase or redirect according to real interview feedback rather than a large arbitrary problem count.

## Practical Python drills

1. Implement an LRU cache with specified eviction and empty-capacity behavior.
2. Merge streamed text fragments and handle incomplete records without data loss.
3. Implement a token-bucket rate limiter with an injected clock for deterministic tests.
4. Build a bounded async worker pool with cancellation and clean shutdown.
5. Retry a transient operation with bounded attempts, jitter and an overall deadline.
6. Deduplicate idempotent ingestion requests while detecting conflicting payloads.
7. Parse benchmark records and preserve failures and missing values.
8. Implement top-k exact vector search and compare it to a reference.
9. Create a batcher with a maximum size and maximum wait time; explain latency tradeoffs.
10. Design a small model-switch state machine and test cancel/load failure transitions.
11. Write a streaming HTTP client with timeout and error handling against a local mock.
12. Repair an intentionally blocking call inside an async service and explain the alternative.

Implement a narrow version in one session and deepen tests later. Do not pretend a minimal rate limiter is a distributed production implementation. Explain what additional coordination or persistence would be needed.

## Python depth checklist

Understand mutable defaults, references and copying, iterators/generators, context managers, exceptions, typing, dataclasses, dependency boundaries and testing. Explain the GIL without claiming that async makes CPU work parallel. Distinguish concurrency, parallelism, threads and processes. Explain backpressure and cancellation propagation in an async service. Read code as well as writing new functions.

## Backend and data fundamentals

Practice HTTP semantics, status codes, streaming, retries, idempotency, queues, dead-letter handling, timeouts and graceful shutdown. Know how to choose object storage versus a relational/document database and how index/version metadata fits together. Practice SQL joins, grouping, window functions, transaction basics and index reasoning. Use a local small dataset; do not claim database tuning expertise from memorized terms.

Your RabbitMQ/MongoDB/MinIO experience gives you real stories. Explain delivery guarantees, duplicate handling, consistency boundaries and recovery, not just which components were in Docker Compose. Know where an operation can succeed before a client timeout and why retrying can duplicate work.

## LLM fundamentals to explain clearly

- Prefill versus decode and why their workloads differ.
- Weight memory versus KV cache versus activations and workspace.
- GQA and context-length effects on cache size.
- Quantization formats, error and kernel support.
- Continuous batching versus request batching and token-processing limits.
- Prefix caching and exact invalidation conditions.
- Speculative decoding: acceptance and drafter overhead, not guaranteed speedup.
- Tensor, pipeline and expert parallelism at conceptual level; distinguish reading from operating experience.
- Tokenization, chat templates, stop tokens and constrained output.
- Retrieval quality, reranking, grounding, citation validity and abstention.
- Evaluation design, leakage, held-out sets and limits of judge models.
- Fine-tuning versus retrieval versus prompting as responses to different failures.

For each, prepare a plain-language explanation, a small calculation or example, and a failure case. Use your own public experiments when possible.

## Four system-design cases

**Case A — document intelligence:** ingest large documents, store versions, run extraction, retrieve evidence, answer with citations and support review. Discuss incremental ingestion, document provenance, idempotency, retries, evaluation and updates. Separate indexing from query latency.

**Case B — constrained inference service:** serve a small model on limited GPU memory with short and long requests. Discuss admission control, context/output limits, queueing, batching, cache, cancellation, observability, overload and quality. State SLOs as assumptions, estimate capacity, then propose a benchmark.

**Case C — model residency and switching:** share a GPU between OCR and a generator. Define ownership and state transitions, requests in flight, unload/load, warmup, cache validity, failure rollback and readiness. This is close to your experience; explain the invariant that prevents work from touching unloaded state.

**Case D — remote AI product backend:** support multiple tenants, streaming responses, retries, metering and evaluation. Discuss isolation, rate limits, auditability, timeout budgets, API compatibility and rollout. Avoid naming infrastructure without explaining the failure it solves.

For a 45-minute design: 5 clarify, 5 estimate and define SLOs, 10 data flow and APIs, 10 critical tradeoffs, 10 failure/measurement discussion, 5 summarize. Adjust to interviewer steering. Draw a compact diagram and explain what each boundary owns.

## Debugging cases

1. Throughput drops after a runtime upgrade: compare workload/build/backend, graphs, memory and scheduler behavior before changing settings.
2. TTFT rises but decode is unchanged: inspect queueing, preparation, tokenization and prefill, with timing boundaries.
3. OOM occurs only on long requests: inspect cache/workspace growth, concurrency and admission policy.
4. Cancelled requests retain memory: inspect ownership, outstanding tasks/callbacks and allocator behavior.
5. An OCR result looks plausible but has wrong columns: isolate structural correctness from text recognition and use source-grounded evaluation.
6. A quantized model is smaller but slower: verify kernel/backend support, unpacking and data movement.
7. A queue retries indefinitely: classify permanent/transient failures and impose retry/dead-letter policies.
8. A judge score improves while user trust falls: inspect rubric, unsupported claims, dataset leakage and human review.

Answer with hypotheses, discriminating observations and the next smallest experiment. Do not guess a configuration flag as the whole diagnosis.

## Mock scorecard

Score 0–3 each for clarification, correctness, test coverage, complexity/tradeoffs, explanation and recovery from mistakes. Save the actual failing part: missing edge case, weak Python, slow reasoning, vague ownership or unsubstantiated metric. One mock followed by a repaired implementation is more valuable than repeatedly performing the same weak answer.

## Take-home assessments

Clarify expected time, evaluation criteria, allowed tools and deliverables. Prioritize a correct small implementation, tests, clear README and limitations. Do not expand into an unpaid production service without agreed scope. Follow any explicit AI-use rules. Use human-authored explanations you can defend and avoid exposing employer code.

Practice an asynchronous update containing current status, evidence, blocker, options and next action. Write a small RFC that another engineer can review without a call. Explain time-zone availability honestly and ask about required overlap. Good written engineering communication is both an interview skill and a useful public artifact.

Start with opportunities and applications. Add the other trackers only as activity occurs. Unknown fields remain blank or explicitly unknown. Use consistent company and role identifiers so conversations do not inflate application counts. Track actual source dates separately from job posting dates.

Fit score is a prioritization aid defined in the job-search guide, not a hiring probability. The public status of a contribution must distinguish local, submitted, under review, merged and closed. The post tracker uses platform analytics only where available. Offer values must keep recurring cash separate from one-time bonuses and speculative equity.

Review by cohort and allow response lag. Do not optimize a conversion rate by deleting rejected or failed records.

# Contribution preparation checklist

This is an internal checklist. Write actual issue/PR communication yourself according to the target project's current policy, especially llama.cpp's inspected prohibition on AI-written GitHub posts.

- [ ] Read current contribution instructions, applicable AGENTS files and AI policy.
- [ ] Confirm issue state and inspect related/duplicate PRs.
- [ ] Check hardware and test feasibility.
- [ ] Establish expected versus observed behavior with public inputs.
- [ ] Save minimal reproduction, versions and complete error.
- [ ] Agree feature scope if required.
- [ ] Write an independent failing regression check.
- [ ] Make a focused change that fixes the stated behavior.
- [ ] Run relevant tests and record exact coverage/limitations.
- [ ] Inspect every changed line and explain ownership/numeric effects.
- [ ] Follow CLA/DCO/sign-off and disclosure rules.
- [ ] State public status accurately: local, submitted, under review, merged or closed.
- [ ] Respond to feedback without unrelated scope expansion.
